# 01 · 전체 구조와 "API 없이"의 원리

## 1. 광고된 기능 → 기술 블록

| 기능 | 사용자에게 보이는 것 | 실제로 필요한 기술 | 생성형 AI 필요? |
|---|---|---|---|
| 소재 추천 | "오늘 그릴 소재" 한 줄 | 데이터 뱅크(JSON) + 가중 랜덤 + 슬롯 템플릿 | 아니오 |
| 스토리 · 컷 아이디어 | 4컷/6컷 각 컷에 뭘 넣을지 | 비트 시트 템플릿 + 슬롯 채우기 | 아니오 |
| 캐릭터 생성 | 버튼 누를 때마다 새 캐릭터 | 파츠(머리·눈·입·옷) 레이어 합성 + 색상 치환 | 아니오 |
| 시안 컷 생성 | 캐릭터+배경+말풍선 러프 | Canvas 2D 합성 + 텍스트 줄바꿈 + PNG 저장 | 아니오 |
| 인스타 미리보기 | 업로드 전 피드/캐러셀 모습 | 비율 맞는 HTML 목업 + 글자 수 검사 | 아니오 |

다섯 기능 모두 외부 AI 없이 구현된다. 이것이 "API 없이"가 성립하는 첫 번째 이유다.

## 2. "API 없이"가 가능한 4가지 방식

| 방식 | 원리 | 장점 | 단점 | 판별법 |
|---|---|---|---|---|
| **A. 완전 로컬 규칙 기반** | 미리 써 둔 문장·템플릿과 그려 둔 파츠를 JS가 조합 | 서버비 0, 오프라인 OK, 작가 스타일 일정 | 조합 유한, 데이터 적으면 반복 | 와이파이 꺼도 전부 작동. 파일 수 MB |
| **B. 프롬프트 생성기** | 프로그램이 프롬프트를 만들고 사용자가 ChatGPT 등에 붙여넣기 | AI 품질, 키 불필요 | 복붙 수작업 | "복사" 버튼, "붙여넣으세요" 안내 |
| **C. 브라우저 내 모델** | WebLLM, transformers.js, ONNX Runtime Web | 진짜 생성, 키 불필요 | 수백 MB~GB 다운로드, 저사양 느림 | 첫 실행 긴 로딩, Network 탭에 모델 파일 |
| **D. 개발자 서버 프록시** | 키를 개발자 서버에 숨김 | 사용자는 키 몰라도 됨 | 개발자가 매달 비용, 오프라인 불가 | 와이파이 끄면 멈춤, Network 탭 외부 요청 |

### HITS 추정: A 중심 + B 일부
근거
1. 일회성 35,000원 가격 → D면 구독제여야 수지가 맞음.
2. 아임웹 '유료 콘텐츠' 다운로드 판매 → 파일형 상품.
3. 판매자가 표정 240장·포즈·만화적 표현 가이드 등 그림 자산 보유 → 캐릭터 생성은 파츠 조합으로 보는 게 자연스러움.
4. "웹용 서포터 프로그램" 표현 → 브라우저에서 여는 파일.

### 구매 후 판별 체크리스트
- [ ] 파일 확장자와 용량 (html 1개? zip? 수 MB vs 수백 MB)
- [ ] 와이파이 끄고 모든 버튼 실행 → 전부 되면 A(+B)
- [ ] 브라우저 개발자도구 Network 탭에 외부 요청이 있는가 → 있으면 그 기능은 C 또는 D
- [ ] "복사" 버튼과 외부 AI 안내 문구 → B 혼합
- [ ] 첫 실행 로딩 시간 → 길면 C

## 3. 추정 아키텍처 (단일 HTML 파일 안의 5층)

```
┌──────────────────────── 하나의 HTML 파일 (서버 없음) ────────────────────────┐
│ ① UI 층        탭: 소재 · 스토리 · 캐릭터 · 시안 · 미리보기 (버튼, 입력창)   │
│        ↓                                   ↓                                  │
│ ② 로직 층 (조합 엔진)            ← →   ③ 데이터 층 (작가의 자산)             │
│   · 시드 난수                            · 소재 뱅크 JSON (상황/감정/관계/반전)│
│   · 슬롯 템플릿 채우기                   · 스토리 템플릿 (공감형/썰형/정보형)  │
│   · 가중 랜덤 + 중복 회피                · 캐릭터 파츠 (SVG/PNG base64)        │
│   · 비트 시트 분배                       · 말풍선 · 효과선 · 배경 프리셋       │
│        ↓                                                                      │
│ ④ 렌더 층                        ← →   ⑤ 저장 · 내보내기                    │
│   · Canvas 2D 레이어 합성 → PNG          · localStorage 자동 저장              │
│   · DOM 목업 (4:5 프레임, 3열 그리드)    · 프로젝트 JSON 내보내기/불러오기     │
│   · 텍스트 줄바꿈, 말풍선 자동 크기      · canvas.toBlob → PNG 다운로드        │
└───────────────────────────────────────────────────────────────────────────────┘
흐름: 버튼 → 로직이 데이터에서 조각을 뽑아 조합 → 렌더 → 저장/내보내기. 외부 요청 없음.
```

핵심은 **②와 ③의 분리**. 엔진(②)은 작고 범용적이며, 결과물 품질과 "작가 느낌"은 전부 데이터(③)에서 나온다.

## 5. 상태 객체 한 장으로 전체를 설명하기

모든 기능은 아래 객체 하나를 읽고 쓴다. 그림 자체는 저장하지 않고 "선택값"만 저장한다 (07 참조).

```js
const state = {

  cuts: [ { bg: "room", chars: [ { ref: "main", x: 300, y: 500, scale: 1 } ], bubbles: [ { text: "...", x: 120, y: 160 } ] } ],
  preview: { ratio: "4:5", caption: "", hashtags: [] }

```

## 6. 개발 순서 (4단계)

1. **데이터 설계** (가장 오래 걸림) — 슬롯별 최소 30개, 파츠 종류별 5개 이상. 스프레드시트 → JSON.
2. **조합 엔진** (하루) — `rng`, `pick`, `fill` 세 함수. "다시 / 고정 / 복사" 버튼.
3. **렌더·미리보기** (2~3일) — 1080×1350 캔버스, 4:5 프레임·3열 그리드 목업, PNG 내보내기.
4. **단일 HTML로 묶어 판매** — 이미지 인라인, 압축, 디지털 파일 상품 등록. 첫 버전은 기능을 줄이고 데이터 품질에 집중.
